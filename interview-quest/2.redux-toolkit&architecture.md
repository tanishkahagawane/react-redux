27. **Why was Redux Toolkit introduced?**

27\. Why was Redux Toolkit introduced?

Redux Toolkit (RTK) was introduced to simplify Redux development and reduce the amount of boilerplate code required to manage application state.

Key reasons:

1. Less boilerplate: Reduces the need to write repetitive action types, action creators, and reducers.
2. Simpler store configuration: Provides `configureStore()` with useful defaults, including Redux DevTools integration.
3. Simplified reducers: Uses `createSlice()` and Immer to allow writing update logic that looks like direct state mutation while keeping state updates immutable.
4. Built-in best practices: Includes sensible defaults and middleware to help prevent common mistakes.
5. Easy asynchronous logic: Supports async operations using `createAsyncThunk()`.
6. Better developer experience: Makes Redux code easier to write, maintain, and debug.

Example:

```
import { createSlice, configureStore } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => {
      state.value += 1;
    }
  }
});

const store = configureStore({
  reducer: {
    counter: counterSlice.reducer
  }
});
```

Interview conclusion: Redux Toolkit was introduced as the official, recommended way to write Redux logic. It reduces boilerplate, simplifies store and reducer setup, and provides built-in tools and best practices for efficient state management.

28. What problems with traditional Redux does RTK solve?

28\. What problems with traditional Redux does Redux Toolkit (RTK) solve?

Redux Toolkit solves several problems associated with traditional Redux, mainly by reducing boilerplate code and simplifying state management.

Key problems it solves:

1. Too much boilerplate: Traditional Redux requires separate action types, action creators, and reducers. RTK simplifies this using `createSlice()`.
2. Complex store configuration: Setting up the Redux store and middleware manually can be complicated. RTK provides `configureStore()` with sensible defaults.
3. Immutable state updates: Traditional Redux requires manually creating new state objects using techniques like the spread operator. RTK uses Immer, allowing simpler update logic while maintaining immutability.
4. Complex asynchronous logic: Handling API calls and async actions often requires additional setup. RTK provides `createAsyncThunk()` to simplify asynchronous operations.
5. Common coding mistakes: RTK includes development checks and default middleware to help detect issues such as accidental state mutations.
6. Redux DevTools setup: RTK automatically integrates Redux DevTools support through `configureStore()`.

Example: Traditional Redux vs RTK

Traditional Redux:

```
const INCREMENT = 'INCREMENT';

const increment = () => ({
  type: INCREMENT
});

function counterReducer(state = { value: 0 }, action) {
  switch (action.type) {
    case INCREMENT:
      return { ...state, value: state.value + 1 };
    default:
      return state;
  }
}
```

Redux Toolkit:

```
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => {
      state.value += 1;
    }
  }
});
```

Interview conclusion: Redux Toolkit addresses the complexity and boilerplate of traditional Redux by providing simpler APIs, immutable state update handling, easier asynchronous logic, and better default configurations. It makes Redux applications easier to develop, maintain, and debug.

## 29. Explain `configureStore()`, `createSlice()`, `createAsyncThunk()`, and `createSelector()`.

These are important Redux Toolkit APIs used to configure the Redux store, manage state, handle asynchronous operations, and optimize derived data.

### 1. `configureStore()`

Purpose: Creates and configures the Redux store with sensible default settings.

- Combines multiple reducers.
- Automatically sets up useful middleware.
- Enables Redux DevTools integration.
- Includes development checks for common mistakes.

Example:

```
import { configureStore } from '@reduxjs/toolkit';
import counterReducer from './counterSlice';

const store = configureStore({
  reducer: {
    counter: counterReducer
  }
});

export default store;
```

Interview answer: `configureStore()` simplifies Redux store setup by automatically configuring middleware, DevTools integration, and reducer combination.

### 2. `createSlice()`

Purpose: Creates a Redux slice containing the slice name, initial state, reducers, and automatically generated action creators.

- Reduces boilerplate code.
- Generates action types and action creators automatically.
- Uses Immer to handle immutable state updates.

Example:

```
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => {
      state.value += 1;
    },
    decrement: (state) => {
      state.value -= 1;
    }
  }
});

export const { increment, decrement } = counterSlice.actions;
export default counterSlice.reducer;
```

Interview answer: `createSlice()` combines action types, action creators, and reducer logic into one place, making Redux code simpler and easier to maintain.

### 3. `createAsyncThunk()`

Purpose: Simplifies handling asynchronous operations, such as API calls.

It automatically generates three action types for the async operation:

- `pending` — the request has started.
- `fulfilled` — the request completed successfully.
- `rejected` — the request failed.

Example:

```
import { createAsyncThunk, createSlice } from '@reduxjs/toolkit';

export const fetchUsers = createAsyncThunk(
  'users/fetchUsers',
  async () => {
    const response = await fetch('/api/users');

    if (!response.ok) {
      throw new Error('Failed to fetch users');
    }

    return response.json();
  }
);

const usersSlice = createSlice({
  name: 'users',
  initialState: {
    data: [],
    loading: false,
    error: null
  },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUsers.pending, (state) => {
        state.loading = true;
        state.error = null;
      })
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.loading = false;
        state.data = action.payload;
      })
      .addCase(fetchUsers.rejected, (state, action) => {
        state.loading = false;
        state.error = action.error.message;
      });
  }
});

export default usersSlice.reducer;
```

Interview answer: `createAsyncThunk()` handles the lifecycle of asynchronous tasks by generating pending, fulfilled, and rejected actions, allowing us to manage loading, success, and error states.

### 4. `createSelector()`

Purpose: Creates memoized selectors that derive data from the Redux store.

- Avoids recalculating derived values when input values have not changed.
- Helps prevent unnecessary recalculations.
- Keeps data transformation logic reusable and organized.

Example:

```
import { createSelector } from '@reduxjs/toolkit';

const selectProducts = (state) => state.products.items;

const selectExpensiveProducts = createSelector(
  [selectProducts],
  (products) => products.filter((product) => product.price > 1000)
);
```

Usage:

```
const expensiveProducts = selectExpensiveProducts(store.getState());
```

Here, the filtering operation is recalculated only when the `products` input reference changes.

Interview answer: `createSelector()` creates memoized selectors that efficiently calculate derived data and avoid unnecessary recalculations when their input values remain unchanged.

## Quick revision table

| API                  | Main purpose                                                |
| -------------------- | ----------------------------------------------------------- |
| `configureStore()`   | Creates and configures the Redux store                      |
| `createSlice()`      | Creates reducers and action creators together               |
| `createAsyncThunk()` | Handles asynchronous operations and their lifecycle actions |
| `createSelector()`   | Memoizes derived data to avoid unnecessary recalculations   |

Easy way to remember:

- `configureStore` → Store setup
- `createSlice` → State and reducers
- `createAsyncThunk` → Async operations
- `createSelector` → Derived data and memoization

30. What does `createSlice()` generate automatically?

30\. What does `createSlice()` generate automatically?

In Redux Toolkit, `createSlice()` automatically generates action creators and action type strings based on the slice name and the reducer functions we define.

It provides:

1. Action types: Generates action type strings using the slice name and reducer name.
2. Action creators: Creates functions for each reducer that return the corresponding action object.
3. Reducer function: Generates a reducer that handles the actions defined in the slice.
4. Initial state handling: Uses the initial state provided in the slice configuration.

### Example

```
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => {
      state.value += 1;
    },
    decrement: (state) => {
      state.value -= 1;
    }
  }
});
```

Access the generated values:

```
counterSlice.actions.increment();
// { type: 'counter/increment', payload: undefined }

counterSlice.actions.decrement();
// { type: 'counter/decrement', payload: undefined }

counterSlice.reducer; // Generated reducer function
```

We can also export them:

```
export const { increment, decrement } = counterSlice.actions;
export default counterSlice.reducer;
```

### Interview answer

`createSlice()` automatically generates action type strings, action creator functions, and a reducer function from the slice name, initial state, and reducer definitions. It reduces boilerplate code and makes Redux state management easier.

In Redux Toolkit, `createSlice()` automatically generates action creators and a reducer based on the slice name and the reducers we define.

```
counterSlice.actions.increment()
```

We can dispatch it using:

```
dispatch(counterSlice.actions.increment());
```

### 2. Generated reducer

```
counterSlice.reducer
```

This reducer handles the `"counter/increment"` action and increments the state by `1`.

For example:

```
counterSlice.reducer(0, counterSlice.actions.increment());
// Returns: 1
```

- `initialState: 0` sets the initial state to a number.
- `increment` defines the reducer logic that returns `state + 1`.
- `createSlice()` generates the action creator and the slice reducer automatically.

Important interview point: Since `state` is a number (a primitive value), returning `state + 1` correctly updates the state. Redux Toolkit uses Immer internally, but here we return the new value directly.

32. How does RTK allow this?

```js
state.user.name = "John";
```

if Redux state is supposed to be immutable?

Interview Answer:

Redux Toolkit allows this syntax because it uses Immer internally.

Normally, Redux state must be immutable, meaning we should not directly modify the existing state. However, RTK uses Immer to let us write code that looks like mutation while producing a new immutable state.

### Example

```
const userSlice = createSlice({
  name: "user",
  initialState: {
    user: {
      name: "Alice",
    },
  },
  reducers: {
    updateName: (state) => {
      state.user.name = "John";
    },
  },
});
```

Here, `state.user.name = "John"` looks like direct mutation, but Immer handles it internally.

### How does it work?

1. Draft state: Immer provides a draft of the current state through a Proxy.
2. Track changes: When we write `state.user.name = "John"`, Immer records the modification to the draft.
3. Create new state: Immer produces a new state object containing the changes while preserving the original state.
4. Preserve references: Unchanged parts of the state can retain their original references, improving performance.

### Important interview point

RTK supports two approaches inside a reducer:

```
// Approach 1: Mutation-style syntax
updateName: (state) => {
  state.user.name = "John";
},

// Approach 2: Return a new state
increment: (state) => state + 1,
```

Both approaches are valid in Redux Toolkit.

Remember: You should either mutate the draft state or return a new state from a reducer—not both in the same reducer execution.

In short: Redux still follows immutability. Immer, integrated into Redux Toolkit's `createSlice()`, handles immutable updates behind the scenes, allowing us to write simpler, mutation-like code.

33. What is **Immer** and how does Redux Toolkit use it?

Interview Answer: What is Immer, and how does Redux Toolkit use it?

Immer is a JavaScript library that lets us write code that looks like it mutates an object while producing a new immutable state behind the scenes.

Redux Toolkit uses Immer internally in `createSlice()` and `createReducer()` to simplify state updates.

### 1. Example without Immer

In traditional Redux, we create a new state object instead of modifying the existing state.

```
const newState = {
  ...state,
  user: {
    ...state.user,
    name: "John",
  },
};
```

This can become complicated when updating deeply nested objects.

### 2. Example with Immer in Redux Toolkit

```
const userSlice = createSlice({
  name: "user",
  initialState: {
    name: "Alice",
    age: 25,
  },
  reducers: {
    updateName: (state) => {
      state.name = "John";
    },
  },
});
```

Here, `state.name = "John"` looks like mutation, but Immer tracks the change and produces a new immutable state.

### 3. How Immer works

1. Creates a draft: Immer provides a draft of the current state using a Proxy.
2. Tracks changes: It detects modifications made to the draft.
3. Produces new state: It creates the next immutable state based on those changes.
4. Preserves unchanged references: Unmodified parts of the state can reuse their existing references.

### 4. Important interview points

- Immer is integrated into Redux Toolkit; you generally don't need to install or use it separately.
- Mutation-style updates are safe inside RTK case reducers because Immer handles them.
- You should either mutate the draft or return a replacement state, not both.
- This behavior applies to reducers created with `createSlice()` and `createReducer()`, not to arbitrary Redux reducers.

In short: Immer simplifies Redux state updates by allowing mutation-like syntax while preserving immutability internally. This makes reducers easier to read, write, and maintain.

34. What's the difference between:

```js
reducers;
extraReducers;
```

Interview Answer: Difference between `reducers` and `extraReducers` in Redux Toolkit

Both are used inside `createSlice()`, but they serve different purposes.

- `reducers` defines the slice's own reducer logic and automatically generates corresponding action creators.
- `extraReducers` handles actions defined elsewhere, such as actions from `createAsyncThunk()` or actions generated by another slice. It does not generate action creators.

### 1. `reducers` example

```
const counterSlice = createSlice({
  name: "counter",
  initialState: 0,
  reducers: {
    increment: (state) => state + 1,
    decrement: (state) => state - 1,
  },
});

counterSlice.actions.increment();
counterSlice.actions.decrement();
```

Here, Redux Toolkit automatically generates the `increment` and `decrement` action creators.

### 2. `extraReducers` example

```
const fetchUser = createAsyncThunk(
  "user/fetchUser",
  async () => {
    const response = await fetch("/api/user");
    return response.json();
  }
);

const userSlice = createSlice({
  name: "user",
  initialState: {
    data: null,
    loading: false,
  },
  reducers: {
    clearUser: (state) => {
      state.data = null;
    },
  },
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => {
        state.loading = true;
      })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.loading = false;
        state.data = action.payload;
      })
      .addCase(fetchUser.rejected, (state) => {
        state.loading = false;
      });
  },
});
```

Here, `extraReducers` handles the `pending`, `fulfilled`, and `rejected` actions generated by `createAsyncThunk()`.

### 3. Key differences

| Feature                   | `reducers`                     | `extraReducers`                        |
| ------------------------- | ------------------------------ | -------------------------------------- |
| Purpose                   | Define the slice's own actions | Handle existing actions                |
| Generates action creators | Yes                            | No                                     |
| Typical use               | Increment, reset, update data  | Async thunk lifecycle actions          |
| Action source             | Defined inside the slice       | Defined outside the slice or elsewhere |
| Syntax                    | Object of reducer functions    | Usually a builder callback             |

### 4. Important interview point

Both can update the same slice state, and both support Immer's mutation-style syntax.

In short: Use `reducers` when you want to define actions for your slice. Use `extraReducers` when your slice needs to respond to actions defined elsewhere, especially async thunk lifecycle actions.

```
import { createSlice, createAsyncThunk } from "@reduxjs/toolkit";

export const fetchUser = createAsyncThunk(
```

### 2. Why do we use `extraReducers` here?

`createAsyncThunk()` automatically generates three lifecycle actions:

- `pending` — the API request has started.
- `fulfilled` — the API request succeeded.
- `rejected` — the API request failed.

We use `extraReducers` to handle these actions and update the slice state accordingly.

### 3. Other use cases

We can also use `extraReducers` when:

- One slice needs to respond to actions created by another slice.

### Important interview point

Unlike `reducers`, `extraReducers` does not generate new action creators. It only lets the slice respond to existing actions.

In short: Use `extraReducers` when a slice needs to handle external actions, especially `createAsyncThunk()` lifecycle actions, to manage API loading, success, and error states.

36. Explain `createAsyncThunk`.

Interview Answer: What is `createAsyncThunk` in Redux Toolkit?

`createAsyncThunk` is a Redux Toolkit function used to handle asynchronous operations, such as API calls. It automatically generates three lifecycle actions: `pending`, `fulfilled`, and `rejected`.

We typically use these actions with `extraReducers` to manage loading, success, and error states.

## 1. Example

```
import { createAsyncThunk, createSlice } from "@reduxjs/toolkit";

// 1. Create an async thunk
export const fetchUsers = createAsyncThunk(
  "users/fetchUsers",
  async () => {
    const response = await fetch("/api/users");

    if (!response.ok) {
      throw new Error("Failed to fetch users");
    }

    return response.json();
  }
);

// 2. Create a slice
const usersSlice = createSlice({
  name: "users",
  initialState: {
    data: [],
    loading: false,
    error: null,
  },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUsers.pending, (state) => {
        state.loading = true;
        state.error = null;
      })
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.loading = false;
        state.data = action.payload;
      })
      .addCase(fetchUsers.rejected, (state, action) => {
        state.loading = false;
        state.error = action.error.message;
      });
  },
});

export default usersSlice.reducer;
```

## 2. How does it work?

Dispatch thunk

`dispatch(fetchUsers())`

`pending`

Set loading to true

`fulfilled`

Store response data

`rejected`

Store error information

1. Dispatching `fetchUsers()` starts the asynchronous operation.
2. Redux Toolkit dispatches the `pending` action.
3. If the promise resolves, it dispatches `fulfilled` with the result in `action.payload`.
4. If the promise rejects or the payload creator throws an error, it dispatches `rejected`.

## 3. How do we call it in a component?

```
import { useDispatch, useSelector } from "react-redux";
import { useEffect } from "react";
import { fetchUsers } from "./usersSlice";

function Users() {
  const dispatch = useDispatch();
  const { data, loading, error } = useSelector(
    (state) => state.users
  );

  useEffect(() => {
    dispatch(fetchUsers());
  }, [dispatch]);

  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error: {error}</p>;

  return (
    <ul>
      {data.map((user) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

## 4. Key interview points

- `createAsyncThunk` simplifies handling asynchronous logic in Redux.
- It generates `pending`, `fulfilled`, and `rejected` action creators automatically.
- `extraReducers` handles those actions and updates the state.
- The fulfilled result is available through `action.payload`.
- Errors can be handled through `action.error` or by using `rejectWithValue()` to return a custom error payload.
- It does not automatically create a loading state or store API data; we implement that logic in our reducers.

In short: `createAsyncThunk` manages the lifecycle of asynchronous tasks, while `extraReducers` updates the Redux state based on whether those tasks are pending, successful, or failed.

37. What are the lifecycle actions generated by `createAsyncThunk`?

```text
pending
fulfilled
rejected
```

Interview Answer:

`createAsyncThunk` automatically generates three lifecycle actions to represent the different stages of an asynchronous operation, such as an API request.

### 1. `pending`

Dispatched when the async operation starts.

```
builder.addCase(fetchUsers.pending, (state) => {
  state.loading = true;
});
```

Purpose: Show a loading indicator while the request is in progress.

### 2. `fulfilled`

Dispatched when the async operation completes successfully.

```
builder.addCase(fetchUsers.fulfilled, (state, action) => {
  state.loading = false;
  state.data = action.payload;
});
```

Purpose: Store the successful response data in the Redux state. The returned value is available in `action.payload`.

### 3. `rejected`

Dispatched when the async operation fails or is rejected.

```
builder.addCase(fetchUsers.rejected, (state, action) => {
  state.loading = false;
  state.error = action.error.message;
});
```

Purpose: Stop the loading indicator and handle the error.

## Quick comparison

| Lifecycle action | When it runs     | Typical use            |
| ---------------- | ---------------- | ---------------------- |
| `pending`        | Request starts   | Set loading to `true`  |
| `fulfilled`      | Request succeeds | Save response data     |
| `rejected`       | Request fails    | Save error information |

### Important interview point

For a thunk named `fetchUsers`, Redux Toolkit generates action types such as:

```
"users/fetchUsers/pending"
"users/fetchUsers/fulfilled"
"users/fetchUsers/rejected"
```

These action creators are available as `fetchUsers.pending`, `fetchUsers.fulfilled`, and `fetchUsers.rejected`.

In short: `pending` indicates the operation has started, `fulfilled` indicates success, and `rejected` indicates failure. We usually handle all three using `extraReducers` to manage loading, data, and error states.

38. How do you handle loading/error/success states with `createAsyncThunk`?

Interview Answer:

We handle loading, error, and success states with `createAsyncThunk` by using its three lifecycle actions — `pending`, `fulfilled`, and `rejected` — inside `extraReducers`.

- `pending`: Set loading to `true`.
- `fulfilled`: Store the response data and set loading to `false`.
- `rejected`: Store the error message and set loading to `false`.

### 1. Example

```
import { createSlice, createAsyncThunk } from "@reduxjs/toolkit";

export const fetchUsers = createAsyncThunk(
  "users/fetchUsers",
  async () => {
    const response = await fetch("/api/users");

    if (!response.ok) {
      throw new Error("Failed to fetch users");
    }

    return response.json();
  }
);

const usersSlice = createSlice({
  name: "users",
  initialState: {
    data: [],
    loading: false,
    error: null,
  },
  reducers: {},
  extraReducers: (builder) => {
    builder
      // Loading state
      .addCase(fetchUsers.pending, (state) => {
        state.loading = true;
        state.error = null;
      })

      // Success state
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.loading = false;
        state.data = action.payload;
      })

      // Error state
      .addCase(fetchUsers.rejected, (state, action) => {
        state.loading = false;
        state.error = action.error.message;
      });
  },
});

export default usersSlice.reducer;
```

### 2. How it works

Loading

`pending` → `loading = true`

Success

`fulfilled` → save `action.payload` and set `loading = false`

Error

`rejected` → save the error and set `loading = false`

### 3. Accessing the states in a React component

```
const { data, loading, error } = useSelector(
  (state) => state.users
);

if (loading) return <p>Loading users...</p>;
if (error) return <p>Error: {error}</p>;

return data.map((user) => (
  <p key={user.id}>{user.name}</p>
));
```

### Important interview points

- `createAsyncThunk` generates the lifecycle actions automatically.
- `extraReducers` handles these actions and updates the state.
- `action.payload` contains the successful result.
- `action.error.message` provides the default error message when the thunk fails.
- For custom error responses, use `rejectWithValue()` and access the custom error through `action.payload` in the rejected reducer.

In short: We use `pending`, `fulfilled`, and `rejected` in `extraReducers` to manage the complete API request lifecycle in Redux Toolkit.

39. How do you pass parameters to `createAsyncThunk`?

Interview Answer:

In Redux Toolkit, we pass parameters to `createAsyncThunk` as the first argument to the dispatched thunk action. That value is received as the first parameter of the payload creator function.

### 1. Example: Passing a user ID

```
import { createAsyncThunk } from "@reduxjs/toolkit";

export const fetchUserById = createAsyncThunk(
  "users/fetchUserById",
  async (userId) => {
    const response = await fetch(`/api/users/${userId}`);

    if (!response.ok) {
      throw new Error("Failed to fetch user");
    }

    return response.json();
  }
);
```

### 2. Dispatch with a parameter

```
dispatch(fetchUserById(101));
```

Here, `101` is passed to the payload creator as `userId`.

### 3. Passing multiple parameters

If we need to pass multiple values, we usually pass them as an object.

```
export const fetchUser = createAsyncThunk(
  "users/fetchUser",
  async ({ userId, includePosts }) => {
    const response = await fetch(
      `/api/users/${userId}?includePosts=${includePosts}`
    );

    if (!response.ok) {
      throw new Error("Failed to fetch user");
    }

    return response.json();
  }
);
```

Dispatch it like this:

```
dispatch(
  fetchUser({
    userId: 101,
    includePosts: true,
  })
);
```

### 4. Accessing the parameter and `thunkAPI`

The payload creator can accept a second argument, `thunkAPI`, which provides access to tools such as `dispatch`, `getState`, and `rejectWithValue`.

```
export const fetchUser = createAsyncThunk(
  "users/fetchUser",
  async (userId, thunkAPI) => {
    const token = thunkAPI.getState().auth.token;

    const response = await fetch(`/api/users/${userId}`, {
      headers: {
        Authorization: `Bearer ${token}`,
      },
    });

    if (!response.ok) {
      return thunkAPI.rejectWithValue("Failed to fetch user");
    }

    return response.json();
  }
);
```

Important interview point: `createAsyncThunk` accepts one argument for the payload creator's input. To pass multiple values, use an object or array. The second parameter of the payload creator is `thunkAPI`, not another custom argument.

In short: Pass parameters through `dispatch(fetchUserById(101))`, receive them in the payload creator, and use an object when multiple parameters are needed.

40. How do you access `rejectWithValue()`?

Interview Answer:

In Redux Toolkit, `rejectWithValue()` is provided by the `thunkAPI` object inside the `createAsyncThunk` payload creator. We use it to return a custom error payload when an asynchronous operation fails.

### 1. Example: Using `rejectWithValue()`

```
import { createAsyncThunk } from "@reduxjs/toolkit";

export const fetchUser = createAsyncThunk(
  "user/fetchUser",
  async (userId, { rejectWithValue }) => {
    try {
      const response = await fetch(`/api/users/${userId}`);

      if (!response.ok) {
        return rejectWithValue("Failed to fetch user");
      }

      return await response.json();
    } catch (error) {
      return rejectWithValue("Network error occurred");
    }
  }
);
```

Notice that we access `rejectWithValue` by destructuring the second argument, `thunkAPI`.

### 2. How do we access the rejected value?

Inside `extraReducers`, we read the custom error from `action.payload`.

```
extraReducers: (builder) => {
  builder.addCase(fetchUser.rejected, (state, action) => {
    state.loading = false;
    state.error =
      action.payload || action.error.message;
  });
}
```

- `action.payload` contains the custom value passed to `rejectWithValue()`.
- `action.error.message` contains the default error message when the thunk fails without returning a custom rejection value.

### 3. Important interview point

| Property                           | Meaning                                       |
| ---------------------------------- | --------------------------------------------- |
| `rejectWithValue("Error message")` | Returns a custom rejection payload            |
| `action.payload`                   | Contains the custom rejection value           |
| `action.error.message`             | Contains the default serialized error message |

In short: Access `rejectWithValue()` through `thunkAPI` inside the async thunk, then access its custom rejection value through `action.payload` in the `rejected` reducer.

41. What is the difference between:

```js
return rejectWithValue(error);
```

and:

```js
throw error;
```

Interview Answer:

In Redux Toolkit, both `return rejectWithValue(error)` and `throw error` cause the async thunk to enter the `rejected` state, but they handle error information differently.

### 1. `return rejectWithValue(error)`

This lets us return a custom error payload.

```
export const fetchUser = createAsyncThunk(
  "user/fetchUser",
  async (_, { rejectWithValue }) => {
    try {
      const response = await fetch("/api/user");

      if (!response.ok) {
        return rejectWithValue({
          message: "User not found",
          status: response.status,
        });
      }

      return await response.json();
    } catch (error) {
      return rejectWithValue({
        message: "Network error",
      });
    }
  }
);
```

In the rejected reducer:

```
.addCase(fetchUser.rejected, (state, action) => {
  state.error = action.payload;
});
```

The custom error object is available in `action.payload`.

### 2. `throw error`

This rejects the thunk with an error. Redux Toolkit serializes the error into `action.error`.

```
export const fetchUser = createAsyncThunk(
  "user/fetchUser",
  async () => {
    const response = await fetch("/api/user");

    if (!response.ok) {
      throw new Error("Failed to fetch user");
    }

    return await response.json();
  }
);
```

In the rejected reducer:

```
.addCase(fetchUser.rejected, (state, action) => {
  state.error = action.error.message;
});
```

Here, the error message is available in `action.error.message`, not as a custom `action.payload`.

### 3. Key differences

| Feature                | `rejectWithValue(error)`                    | `throw error`                        |
| ---------------------- | ------------------------------------------- | ------------------------------------ |
| Purpose                | Return a custom rejection payload           | Reject with an error                 |
| Error location         | `action.payload`                            | `action.error`                       |
| Custom structured data | Yes                                         | Not preserved as an arbitrary object |
| Typical use            | API validation errors, server error details | Unexpected errors or exceptions      |

### 4. Important interview point

For API errors, `rejectWithValue()` is useful when you want to preserve structured server information, such as a validation message or status code.

For unexpected exceptions, throwing an error is usually appropriate. You can also catch an exception and pass a normalized error to `rejectWithValue()` if you want a consistent error format.

In short: `rejectWithValue()` puts custom error data in `action.payload`, while `throw error` puts serialized error information in `action.error`.

42. How do you cancel an async thunk?

Interview Answer:

In Redux Toolkit, we can cancel an async thunk using the `AbortSignal` and the `abort()` method provided by `createAsyncThunk`.

There are two common steps: use `thunkAPI.signal` inside the async operation, then call `abort()` on the promise returned by dispatching the thunk.

### 1. Pass the abort signal to the API request

```
import { createAsyncThunk } from "@reduxjs/toolkit";

export const fetchUsers = createAsyncThunk(
  "users/fetchUsers",
  async (_, { signal }) => {
    const response = await fetch("/api/users", { signal });

    if (!response.ok) {
      throw new Error("Failed to fetch users");
    }

    return response.json();
  }
);
```

The `signal` allows `fetch()` to stop the network request when the thunk is aborted.

### 2. Cancel the thunk

```
import { useEffect } from "react";
import { useDispatch } from "react-redux";
import { fetchUsers } from "./usersSlice";

function Users() {
  const dispatch = useDispatch();

  useEffect(() => {
    const promise = dispatch(fetchUsers());

    return () => {
      promise.abort();
    };
  }, [dispatch]);

  return <p>Fetching users...</p>;
}
```

When the component unmounts, the cleanup function aborts the thunk.

### 3. Handle cancellation

When the thunk is cancelled, Redux Toolkit dispatches its `rejected` action.

```
extraReducers: (builder) => {
  builder.addCase(fetchUsers.rejected, (state, action) => {
    state.loading = false;

    if (action.meta.aborted) {
      return; // Request was cancelled
    }

    state.error = action.error.message;
  });
}
```

- `action.meta.aborted` indicates that the running thunk was aborted.
- `action.error.message` typically contains `"Aborted"` for an aborted thunk.

### Important interview points

- `dispatch(fetchUsers())` returns a promise-like object with an `abort()` method.
- Pass `thunkAPI.signal` to APIs such as `fetch()` to cancel the underlying request.
- Aborting a thunk does not automatically stop arbitrary asynchronous work unless that work supports cancellation.
- A cancelled thunk normally dispatches `rejected`, not `fulfilled`.

In short: Use `promise.abort()` to cancel a dispatched async thunk and `thunkAPI.signal` to propagate cancellation to the underlying operation.

43. How do you prevent duplicate API requests with `createAsyncThunk`?

Interview Answer:

In Redux Toolkit, we can prevent duplicate API requests using the `condition` option of `createAsyncThunk`.

The `condition` callback checks whether a request should execute before the payload creator runs. If it returns `false`, the API request is skipped.

### 1. Example using `condition`

```
import { createAsyncThunk, createSlice } from "@reduxjs/toolkit";

export const fetchUsers = createAsyncThunk(
  "users/fetchUsers",
  async () => {
    const response = await fetch("/api/users");

    if (!response.ok) {
      throw new Error("Failed to fetch users");
    }

    return response.json();
  },
  {
    condition: (_, { getState }) => {
      const { users } = getState();

      // Skip if a request is already in progress
      if (users.loading) {
        return false;
      }

      return true;
    },
  }
);
```

### 2. Track the loading state

```
const usersSlice = createSlice({
  name: "users",
  initialState: {
    data: [],
    loading: false,
  },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchUsers.pending, (state) => {
        state.loading = true;
      })
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.loading = false;
        state.data = action.payload;
      })
      .addCase(fetchUsers.rejected, (state) => {
        state.loading = false;
      });
  },
});
```

Now, if another `fetchUsers()` call happens while `users.loading` is `true`, the `condition` callback returns `false`, preventing the payload creator from running.

### 3. How does it work?

Dispatch `fetchUsers()`

Check `condition()`

Returns `true`

Run the API request

Returns `false`

Skip the request

### 4. Important interview points

- `condition` runs before the payload creator.
- Returning `false` skips the request.
- By default, a condition-based skip does not dispatch a rejected action. You can enable it with `dispatchConditionRejection: true`.
- You can also check whether data is already available to avoid unnecessary refetching.
- For more advanced request caching, deduplication, and automatic cache management, Redux Toolkit provides RTK Query.

In short: Use `createAsyncThunk`'s `condition` option to prevent unnecessary duplicate requests by checking the Redux state before starting the API call.

44. What is `createEntityAdapter`?

Interview Answer: What is `createEntityAdapter`?

`createEntityAdapter` is a Redux Toolkit utility that simplifies managing collections of entities, such as users, products, or posts, in a normalized state structure.

Instead of storing data as a simple array, it stores entities in two properties:

- `ids`: An array of entity IDs.
- `entities`: An object that maps each ID to its corresponding entity.

### 1. Example

```
import {
  createSlice,
  createEntityAdapter,
} from "@reduxjs/toolkit";

const usersAdapter = createEntityAdapter();

const usersSlice = createSlice({
  name: "users",
  initialState: usersAdapter.getInitialState(),
  reducers: {
    setUsers: usersAdapter.setAll,
    addUser: usersAdapter.addOne,
    updateUser: usersAdapter.updateOne,
    removeUser: usersAdapter.removeOne,
  },
});

export const {
  setUsers,
  addUser,
  updateUser,
  removeUser,
} = usersSlice.actions;

export default usersSlice.reducer;
```

### 2. What does the state look like?

Suppose we add these users:

```
[
  { id: 1, name: "John" },
  { id: 2, name: "Alice" }
]
```

The normalized state looks like this:

```
{
  ids: [1, 2],
  entities: {
    1: { id: 1, name: "John" },
    2: { id: 2, name: "Alice" }
  }
}
```

This makes it easier to access or update an individual entity by ID.

### 3. Built-in CRUD methods

`createEntityAdapter` provides methods for common operations:

| Method       | Purpose                   |
| ------------ | ------------------------- |
| `addOne`     | Add one entity            |
| `addMany`    | Add multiple entities     |
| `setAll`     | Replace all entities      |
| `setOne`     | Add or replace one entity |
| `updateOne`  | Update an existing entity |
| `updateMany` | Update multiple entities  |
| `upsertOne`  | Add or update one entity  |
| `removeOne`  | Remove one entity         |
| `removeAll`  | Remove all entities       |

For example:

```
dispatch(addUser({ id: 3, name: "Sam" }));

dispatch(
  updateUser({
    id: 1,
    changes: { name: "John Smith" },
  })
);

dispatch(removeUser(2));
```

### 4. Selectors

The adapter can also generate selectors to access the normalized data.

```
export const usersSelectors =
  usersAdapter.getSelectors(
    (state) => state.users
  );
```

You can then use:

```
usersSelectors.selectAll(state);
usersSelectors.selectById(state, 1);
usersSelectors.selectIds(state);
usersSelectors.selectTotal(state);
```

### 5. Why use it?

- Reduces boilerplate for CRUD operations.
- Makes individual entities easier to find and update.
- Provides a consistent normalized state structure.
- Generates useful selectors automatically.

In short: `createEntityAdapter` helps manage collections of entities efficiently by normalizing state into `ids` and `entities` and providing built-in CRUD reducers and selectors.

45. When would you use `createEntityAdapter` instead of a normal array?

Interview Answer:

I would use `createEntityAdapter` instead of a normal array when I need to manage a large or frequently updated collection of entities, such as users, products, or messages.

It stores data in a normalized structure using `ids` and `entities`, making it easier to find, update, add, and remove individual items.

### 1. Using a normal array

```
const initialState = {
  users: [
    { id: 1, name: "John" },
    { id: 2, name: "Alice" },
  ],
};

// Updating a user requires finding and copying the item.
const updatedUsers = state.users.map((user) =>
  user.id === 1
    ? { ...user, name: "John Smith" }
    : user
);
```

With a normal array, we often write more code to update or remove items by ID.

### 2. Using `createEntityAdapter`

```
const usersAdapter = createEntityAdapter();

const initialState = usersAdapter.getInitialState({
  loading: false,
});

const usersSlice = createSlice({
  name: "users",
  initialState,
  reducers: {
    updateUser: usersAdapter.updateOne,
    removeUser: usersAdapter.removeOne,
  },
});
```

Now we can update or remove a user easily:

```
dispatch(
  updateUser({
    id: 1,
    changes: { name: "John Smith" },
  })
);

dispatch(removeUser(2));
```

The adapter manages the normalized state and provides reusable CRUD operations.

### 3. Key differences

| Normal array                                     | `createEntityAdapter`                            |
| ------------------------------------------------ | ------------------------------------------------ |
| Simple for small collections                     | Useful for complex entity collections            |
| Often requires manual CRUD logic                 | Provides built-in CRUD helpers                   |
| Finding an item by ID usually requires searching | Entities are indexed by ID                       |
| Manual selector implementation                   | Generates common selectors                       |
| Suitable for simple lists                        | Suitable for frequently updated, normalized data |

### 4. When would I choose each?

- Normal array: A small list of simple data that is mostly displayed and rarely updated individually.
- `createEntityAdapter`: A collection where individual items are frequently added, updated, removed, or accessed by ID.

Important interview point: `createEntityAdapter` does not automatically make every operation faster. Its main benefit is normalized state management and reduced boilerplate. A normal array is perfectly fine when the data structure is simple.

In short: I use `createEntityAdapter` when managing entity collections with frequent individual updates and CRUD operations. For simple lists, a normal array is often sufficient.
