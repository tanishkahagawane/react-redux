### 1. Redux fundamentals — must know

1. **Why do we need Redux when React already has `useState` and `useContext`?**

We need Redux because useContext is only a dependency injection tool rather than a full state management architecture, offering major advantages in performance, predictability, and tooling for large apps.

## Core Differences

- Context is for passing data: useContext makes a value available to a nested tree without prop drilling, but you must write your own state logic (useState/useReducer) on top of it.
- Redux is a complete state container: Redux structures how state updates via actions and pure reducers. [1, 3, 5, 6]

## Why Choose Redux Over useContext?

- Performance and Re-renders: When a Context value updates, every component consuming that context re-renders, even if the specific data it uses didn't change. Redux allows components to subscribe to specific slices of state via useSelector, meaning only components that rely on the changed data re-render. [3, 6, 7, 8, 9]
- Debugging and DevTools: Redux offers the Redux DevTools extension, providing powerful time-travel debugging, action logging, and state inspection. Context lacks dedicated debugging tools.
- Predictable Architecture: Redux forces a strict separation of state update logic. This makes it easier to trace when, why, and how state changed in large codebases.
- Middleware and Ecosystem: Redux supports powerful middleware for handling asynchronous logic (like RTK Query or Redux Thunk), persistence plugins, and logging.

## let's explore exactly when Redux becomes overkill and how tools like Zustand and TanStack Query solve specific problems with much less boilerplate.

## 1. When to Use TanStack Query (Server State)

Most state in modern web applications is server state—data fetched from an API that needs to be cached, updated, and synchronized with the backend.
Historically, developers used Redux to fetch data, store it, handle loading/error states, and manage cache expiration. This required massive amounts of boilerplate (actions, reducers, thunks).
TanStack Query replaces Redux for server state because it automatically handles:

- Caching and background fetching.
- Deduping multiple requests for the same data.
- Automatic loading, error, and success states out of the box.
- Pagination, infinite scroll, and garbage collection of old data.

## If 80% of your global state is just data fetched from a database, TanStack Query can replace Redux entirely.

## 2. When to Use Zustand (Client State)

For the remaining 20% of state that lives strictly on the client (e.g., whether a sidebar is open, user preferences, multi-step form data), Zustand is a lightweight, modern alternative to Redux.
Why choose Zustand over Redux?

- Zero Boilerplate: You can create a fully functional, global store in less than 10 lines of code. There are no providers, actions, or reducers required.
- The Best of Redux, Simplified: Zustand uses the same selector-based approach as Redux (const user = useStore(state => state.user)), meaning components only re-render when their specific slice of state changes.
- No React Context Bottleneck: It updates components directly outside of the React render tree, avoiding the re-render issues of useContext.

2. What problem does Redux solve?

Redux solves the problem of **managing shared application state** in a predictable and centralized way.

It helps when multiple components need to **access or update the same data**, avoiding complicated prop drilling and making state changes easier to track and debug.

3. Explain the **Redux data flow**.
4. What are **Store, Action, Reducer, and Dispatch**?

## Redux relies on a strict unidirectional data flow. This means all data within an application follows the exact same lifecycle pattern, making your app's state highly predictable and easier to debug. [1, 2, 3, 4]

## The 4 Core Steps of the Redux Data Flow

┌─────────────────────────────────────────────────────────┐
│ │
▼ │
[ UI / Component ] ──(Dispatches Action)──► [ Store ] │
▲ │ │
│ (Runs Reducer) │
(Triggers Re-render) │ │
│ ▼ │
[ Updated State ] ◄──(Notifies UI)──── [ Reducer ] │
│ │
└─────────────────────────────────────────────────┘

## 1. An Event Triggers an Action

The cycle begins in the UI when a user interacts with the page (e.g., clicking a button or submitting a form). This interaction triggers an action. An action is a plain JavaScript object that describes what happened: [1, 3, 5, 6, 7]

-
- It must include a type property (a string naming the event).
- It optionally carries a payload (the extra data needed for the update). [1, 3, 8, 9]
-

// Example Action Objectconst addTodoAction = {
type: 'todos/todoAdded',
payload: 'Learn Redux data flow'
};

## 2. The Action is Dispatched to the Store

The component cannot update the state directly. Instead, it sends the action object to the Redux store using the dispatch() method. [1, 6, 10]

// Component dispatches the action
store.dispatch(addTodoAction);

## 3. The Store Runs the Reducer Function

The store receives the action and passes it, along with the current state tree, into the reducer function. Reducers are pure functions that calculate a new state based on the old state and the action. [1, 8, 10]

-
- Reducers operate immutably: they never modify the original state directly.
- Instead, they create a copy of the existing state, make changes to the copy, and return it. [1, 5, 10, 11]
-

// Example Reducerfunction todoReducer(state = { todos: [] }, action) {
switch (action.type) {
case 'todos/todoAdded':
// Returns a brand new state object
return {
...state,
todos: [...state.todos, action.payload]
};
default:
return state;
}
}

## 4. The Store Notifies the UI to Re-render

## Once the reducer returns the new state, the store updates its internal state tree. The store then alerts all UI components that have subscribed to it. Those components extract the updated data they need (often via selectors) and safely re-render to display the fresh data on the screen. [3, 5, 7, 10, 11]

## Summary of Component Roles

| Concept  | Role in the Flow                                                            |
| -------- | --------------------------------------------------------------------------- |
| Store    | The single source of truth that holds the global application state.         |
| Action   | A plain JS object describing "what happened" in the app.                    |
| Reducer  | A pure function that calculates the next state snapshot based on an action. |
| Dispatch | The delivery system used to send actions into the store.                    |

5. Why should Redux state be **immutable**?

Redux state must be immutable (never modified directly) for three primary reasons:

-
- Performance (Shallow Equality Checking): Both [Redux and React-Redux](https://redux.js.org/faq/immutable-data) detect state changes by comparing memory references (oldState === newState) rather than doing expensive deep comparisons of every object property. If you mutate the original object, the reference stays the same, and your UI will fail to re-render. [1, 2, 3]
- Predictability & Debugging: Because every change creates a completely new snapshot of the state, developers can easily track every action. This unlocks powerful dev tools like time-travel debugging, which lets you jump back and forth between past state histories to reproduce bugs. [4, 5, 6]
- Eliminating Side Effects: Redux relies on reducers being pure functions. Keeping data immutable ensures that modifying state in one part of your application doesn't accidentally corrupt or change data in another part. [4, 6]
-

(Note: If you use Redux Toolkit, it uses a library called Immer internally. This allows you to write standard "mutating" syntax like state.value = 1 while automatically generating a safe, immutable copy behind the scenes.)

6. What makes a reducer a **pure function**?
   A reducer is a pure function because it strictly adheres to two fundamental rules:

- Predictable Output (Same Input = Same Output): Given the exact same arguments (state and action), a pure reducer will always return the identical result, no matter how many times or when it is called. It relies only on the data passed directly into it.
- No Side Effects: A pure reducer cannot interact with or modify the "outside world."

To maintain this purity, a reducer must never:

- Mutate the existing state argument directly (it must return a new state object instead).
- Perform asynchronous operations like API fetch requests or promises.
- Call non-deterministic functions like Math.random(), Date.now(), or UUID generators.
- Modify global variables or read directly from local storage.

7. Why should we avoid API calls or side effects inside reducers?
   We should avoid **API calls or side effects inside reducers** because reducers must be **pure and predictable**.

- **Reducers should be fast and synchronous.**
- API calls are **asynchronous** and can produce unpredictable results.
- Side effects can cause the reducer to behave differently for the same input.
- It makes **testing and debugging** much harder.
- Reducers should only **calculate and return the new state**.

Instead, API calls and other side effects should be handled using tools like **middleware, Redux Thunk, or Redux Saga**.

**In short:**  
👉 **Reducer = calculate new state**  
👉 **Middleware/Thunk = handle API calls and side effects**

9. When would you **not use Redux**?

You would **not use Redux** when the application is small or when the state doesn't need to be shared across many components.

For example:

- **Small/simple apps** where `useState` is enough.
- **Local UI state** like opening a modal, toggling a button, or handling a form input.
- When state is only used by **one or a few closely related components**.
- When adding Redux would create **unnecessary complexity and boilerplate**.

**In short:**  
👉 If `useState`, `useReducer`, or Context can handle the state easily, **Redux may not be necessary**.

11. What happens internally when you call `dispatch(action)`?

When you call dispatch(action), Redux kicks off a synchronous, centralized loop to update your application state. The store passes the action through any installed middleware, runs it through your reducer function to compute the new state, saves that state, and finally notifies all subscribed UI components so they can re-render.
Here is the exact step-by-step process that happens internally inside the Redux store:

## 1. The Action Enters the Store

When you invoke dispatch(action), the store receives a plain JavaScript object. This object must contain a type property (which acts as a string identifier) and can optionally carry a payload with new data.

## 2. Middleware Execution (The Pipeline)

Before the action ever reaches your reducers, Redux passes it through a chain of middleware (if you have any configured, like Logger, Thunk, or Saga).

- Each middleware intercepts the action in sequential order.
- Middleware can log the action, alter it, pause it, trigger async side effects, or even dispatch entirely new actions.
- The final middleware calls next(action) to forward the action out of the pipeline and into the core store.

## 3. The Root Reducer Computes the New State

The store takes the current state tree and the action, then passes both directly into your root reducer function:
$$\text{reducer}(\text{previousState}, \text{action}) \rightarrow \text{newState}$$

- Redux runs through your entire reducer tree (including sliced reducers).
- The matching case matches the action type and returns a brand new object representing the updated state.
- If no changes apply, the reducer returns the existing state object reference.

## 4. The Store Updates Its State Reference

The Redux store replaces its old internal state tree object reference with the newly returned state tree object reference. This update happens synchronously and atomically—meaning the state transition is complete the instant the reducer finishes executing.

## 5. Subscribers are Notified (UI Re-renders)

Once the state is saved, the store loops through an internal array of active listeners (callbacks registered via store.subscribe()).

- In React applications, hooks like useSelector act as these listeners.
- useSelector checks if the specific slice of data it is tracking has changed (using strict === reference equality).
- If the reference is different, it triggers a React re-render, updating the UI with the fresh data.

---

## A Look Inside: Conceptual Source Code of dispatch

To demystify this, here is a simplified version of what Redux's internal dispatch function looks like under the hood:

function dispatch(action) {
// 1. Validate that the action is a plain object with a type
if (!isPlainObject(action) || typeof action.type === 'undefined') {
throw new Error('Actions must be plain objects with a type property.');
}

try {
isDispatching = true;
// 2. Call the root reducer with the current state and action
currentState = currentReducer(currentState, action);
} finally {
isDispatching = false;
}

// 3. Notify every single active subscriber
const listeners = (currentListeners = nextListeners);
for (let i = 0; i < listeners.length; i++) {
const listener = listeners[i];
listener();
}

// 4. Return the action (standard Redux architecture requirement)
return action;
}

12. Can Redux have multiple stores? Why is a single store generally preferred?

Yes, **Redux can have multiple stores**, but it is **generally recommended to use a single store** for an application.

### Why is a single Redux store preferred?

1. **Single source of truth** – All application state is kept in one place, making it easier to understand and manage.
2. **Easier state sharing** – Different components can access the same state without needing to synchronize multiple stores.
3. **Simpler debugging** – Redux DevTools can track all state changes and actions in one store.
4. **Predictable updates** – Actions flow through one centralized state-management system.
5. **Better middleware management** – Middleware such as logging, persistence, or API handling can be configured centrally.
6. **Avoids synchronization problems** – Multiple stores can lead to duplicated or inconsistent state.

**Example:** Instead of having separate stores for `user`, `products`, and `cart`, a typical Redux app uses one store with separate **slices/reducers**:

```js
const store = configureStore({
  reducer: {
    user: userReducer,
    products: productsReducer,
    cart: cartReducer,
  },
});
```

So, **multiple stores are technically possible, but a single store with multiple slices is the standard approach for most Redux applications.**

Yes, **that's a prominent scenario**, but it's not the _only_ one.

In a **Micro-Frontend (MFE) architecture**, multiple Redux stores can make sense because each independently developed micro-frontend may own its own state and Redux store.

For example:

```text
Application
├── Micro-Frontend A
│   └── Redux Store A
├── Micro-Frontend B
│   └── Redux Store B
└── Micro-Frontend C
    └── Redux Store C
```

This can provide:

- **Isolation** — one MFE's state doesn't interfere with another's.
- **Independent deployment** — teams can develop and deploy MFEs separately.
- **Independent technologies** — different MFEs can potentially use different state-management approaches.
- **Smaller state boundaries** — each MFE manages only the state it owns.

However, if the micro-frontends need to **frequently share and synchronize state**, multiple stores can become complicated. In that case, a **shared/global store** or another cross-MFE communication mechanism may be preferable.

Other situations can also justify multiple Redux stores—for example, **truly independent React applications on the same page** that don't need to share state.

**Interview-friendly answer:**

> "Yes, Redux supports multiple stores, but a single store is generally preferred because it provides a single source of truth and makes state sharing, debugging, and middleware management simpler. Multiple stores can be appropriate in architectures such as micro-frontends, where independent applications need isolated state and independent deployment."

13. What is middleware in Redux?

### 13. What is Middleware in Redux?

**Redux middleware** is a layer that sits **between dispatching an action and the moment it reaches the reducer**.

It allows you to intercept, modify, delay, or perform additional work based on actions.

```text
Component
   ↓
dispatch(action)
   ↓
Middleware
   ↓
Reducer
   ↓
Store updated
   ↓
UI re-renders
```

### Why do we use middleware?

Common use cases include:

- **Logging** actions and state changes
- Handling **asynchronous operations** such as API calls
- Performing side effects
- Dispatching additional actions
- Error reporting
- Authentication-related logic

### Example

A simple middleware:

```js
const logger = (store) => (next) => (action) => {
  console.log("Action:", action);

  const result = next(action);

  console.log("New state:", store.getState());

  return result;
};
```

Here:

- `store` gives access to the Redux store.
- `next` passes the action to the next middleware/reducer.
- `action` is the dispatched action.

### Common Redux middleware

- **Redux Thunk** — handles async logic and allows dispatching functions.
- **Redux Saga** — manages complex asynchronous workflows using generators.
- **Redux Logger** — logs actions and state changes.

**Interview-friendly answer:**

> "Middleware in Redux is a mechanism that intercepts actions between `dispatch()` and the reducer. It is mainly used for side effects, asynchronous operations, logging, API calls, and other logic that shouldn't be placed inside reducers."

14. How does middleware work between `dispatch()` and the reducer?

In Redux, **middleware sits between `dispatch()` and the reducer**. It intercepts every dispatched action before the action reaches the reducer.

The flow is:

**`dispatch(action)` → middleware → reducer → state update**

For example:

```js
const logger = (store) => (next) => (action) => {
  console.log("Dispatching:", action);

  const result = next(action); // passes action to the next middleware/reducer

  console.log("New state:", store.getState());

  return result;
};
```

### What middleware can do

Middleware can:

- Log actions and state changes.
- Modify or delay actions.
- Dispatch additional actions.
- Perform asynchronous operations such as API calls.
- Block certain actions.
- Handle special action types such as functions or promises.

For example, with Redux Thunk:

```js
dispatch(async (dispatch) => {
  const data = await fetchData();
  dispatch({ type: "DATA_LOADED", payload: data });
});
```

The reducer itself should remain **pure**: it receives the final action and current state, then returns the next state.

So, conceptually:

```text
dispatch(action)
      ↓
middleware  ← logging / async / validation / etc.
      ↓
next(action)
      ↓
reducer(state, action)
      ↓
new state
```

The key idea is that **middleware extends what `dispatch()` can do without putting side effects or extra logic inside reducers**.

16. What is the difference between:

```js
useSelector();
useDispatch();
connect();
```

In **React-Redux**, these three are used to connect React components to the Redux store, but they work differently:

| API             | Purpose                                                | Typical usage                      |
| --------------- | ------------------------------------------------------ | ---------------------------------- |
| `useSelector()` | **Read data** from Redux store                         | Functional components              |
| `useDispatch()` | **Dispatch actions** to Redux store                    | Functional components              |
| `connect()`     | **Connect component to Redux** for reading/dispatching | Older/class or function components |

### 1. `useSelector()`

Used to **get data from the Redux store**.

```js
const count = useSelector((state) => state.counter.count);
```

Whenever the selected value changes, the component re-renders.

---

### 2. `useDispatch()`

Used to **send/dispatch actions** to Redux.

```js
const dispatch = useDispatch();

dispatch({ type: "counter/increment" });
```

You can also dispatch an action creator:

```js
dispatch(increment());
```

---

### 3. `connect()`

`connect()` is the **older Higher-Order Component (HOC) approach**.

```js
const mapStateToProps = (state) => ({
  count: state.counter.count,
});

  increment,
};

```

The Redux state and dispatch functions are injected into the component as **props**.

```text

useDispatch() → "Let me send an action to Redux"
connect()     → "Connect this entire component to Redux"
```

17. How does `useSelector` know when to re-render a component?

`useSelector()` subscribes your component to the **Redux store** and re-runs the selector whenever an action is dispatched.

For example:

```js
const count = useSelector((state) => state.counter.count);
```

The process is roughly:

1. **Component renders** → `useSelector` runs the selector.
2. **Redux action is dispatched** → Redux updates the store.
3. `useSelector` **runs the selector again** with the new state.
4. It compares the **previous selected value** with the new selected value using strict `===` comparison by default.
5. If the value changed → **component re-renders**.
6. If the value is the same → **component does not re-render** because of that selector.

### Example

```js
const count = useSelector((state) => state.counter.count);
```

Suppose the state changes from:

```js
{
  counter: { count: 5 },
  user: { name: "John" }
}
```

to:

```js
{
  counter: { count: 6 },
  user: { name: "John" }
}
```

The selector returns:

```text
Before → 5
After  → 6
```

Since `5 !== 6`, the component re-renders.

But if only the user's name changes:

```text
Before → count = 5
After  → count = 5
```

The selected value is unchanged, so the component **doesn't re-render because of `useSelector`**.

### Important interview point

`useSelector()` does **not** simply compare the entire Redux state. It compares the **value returned by your selector**.

Also, by default:

```js
useSelector(selector);
```

uses **strict reference equality (`===`)**, not deep equality.

That's why this can cause unnecessary re-renders:

```js
const data = useSelector((state) => ({
  name: state.user.name,
  age: state.user.age,
}));
```

A new object is created each time, so its reference is different. In such cases, you can use `shallowEqual` or select individual values.

18. What happens if you do:

```js
const data = useSelector((state) => state.data);
```

and the reducer returns a new `data` object on every dispatch?

If the reducer returns a **new `data` object on every dispatch**, `useSelector` will see it as changed because it uses **reference equality (`===`) by default**.

For example:

```js
const data = useSelector((state) => state.data);
```

If every dispatch produces:

```js
// Previous
state.data === { name: "John" };

// Next
state.data === { name: "John" };
```

Even though the contents are identical:

```js
previousData === nextData; // false
```

because they are different object references.

### Result

Every dispatch → new `data` reference → `useSelector` detects a change → **component re-renders**.

```text
Dispatch
   ↓
Reducer runs
   ↓
New data object created
   ↓
useSelector compares references
   ↓
oldData !== newData
   ↓
Component re-renders
```

### Why this matters

This can cause **unnecessary re-renders**, especially if the reducer creates new objects even when the actual data hasn't changed.

A good Redux reducer should generally preserve references when nothing relevant changed:

```js
if (nothingChanged) {
  return state; // same reference
}
```

And only create new objects when something actually changes:

```js
return {
  ...state,
  data: newData,
};
```

**Interview answer:**

> `useSelector` uses strict reference equality by default. If `state.data` gets a new object reference on every dispatch, the selector considers it changed every time, causing the component to re-render—even if the object's contents are identical.

19. What is the purpose of the **equality function** in `useSelector`?

The **equality function** in `useSelector` tells React-Redux **how to decide whether the selected value has changed**.

By default, `useSelector` uses strict equality:

```js
===
```

### Example

```js
const data = useSelector((state) => state.data);
```

React-Redux effectively checks:

```js
previousData === newData;
```

If `false` → component re-renders.  
If `true` → no re-render from that selector.

### Custom equality function

You can provide a second argument:

```js
const data = useSelector((state) => state.data, equalityFn);
```

For example, `shallowEqual`:

```js
import { useSelector, shallowEqual } from "react-redux";

const data = useSelector(
  (state) => ({
    name: state.user.name,
    age: state.user.age,
  }),
  shallowEqual,
);
```

Here, `shallowEqual` compares the object's **properties** rather than requiring the entire object to have the same reference.

### Why is this useful?

Consider:

```js
const data = useSelector((state) => ({
  name: state.user.name,
  age: state.user.age,
}));
```

This creates a **new object on every selector call**.

With the default `===`:

```text
old object === new object
        ↓
       false
        ↓
re-render
```

With `shallowEqual`:

```text
old.name === new.name
old.age  === new.age
        ↓
same values
        ↓
no re-render
```

### Interview answer

> The equality function determines whether the value returned by `useSelector` should be considered changed. By default, React-Redux uses strict reference equality (`===`). A custom equality function such as `shallowEqual` can be used when selecting objects or multiple values to avoid unnecessary re-renders.

**Key distinction:** the equality function doesn't prevent Redux from updating; it determines whether **your component needs to re-render because its selected value changed**.

20. Compare:

```js
const user = useSelector((state) => state.user);
```

with:

```js
const name = useSelector((state) => state.user.name);
const email = useSelector((state) => state.user.email);
```

The main difference is **what part of the Redux state the component subscribes to**.

| Approach                                            | What it selects      | Re-render behavior                                                                  |
| --------------------------------------------------- | -------------------- | ----------------------------------------------------------------------------------- |
| `useSelector((state) => state.user)`                | Entire `user` object | Re-renders when the `user` object reference changes                                 |
| `useSelector((state) => state.user.name)` + `email` | Individual fields    | Each selector re-runs, and the component re-renders when the selected value changes |

### 1. Selecting the entire object

```js
const user = useSelector((state) => state.user);
```

You get:

```js
user.name;
user.email;
user.age;
// etc.
```

If Redux replaces `state.user` with a new object—even if the field you care about hasn't changed—the selector returns a different reference, so the component can re-render.

### 2. Selecting individual fields

```js
const name = useSelector((state) => state.user.name);
const email = useSelector((state) => state.user.email);
```

Now the component only cares about `name` and `email`.

For example, if `user.age` changes:

```js
state.user = {
  ...state.user,
  age: 30,
};
```

the first approach sees a **new `user` object** and may re-render.

The second approach sees:

```js
name; // same value
email; // same value
```

so it doesn't need to re-render because of that `age` change.

### Which is better?

**Use the first approach** when the component genuinely needs most/all of the user object.

**Use individual selectors** when the component only needs specific fields. This makes the component's dependencies clearer and can avoid unnecessary re-renders.

One important detail: calling `useSelector` multiple times is fine. React-Redux batches updates from multiple selectors in the same component, so using two selectors does **not** mean you'll necessarily get two separate renders.

21. What is a selector?

A **selector** is a function that **selects a specific piece of data from the Redux store**.

### Example

```js
const name = useSelector((state) => state.user.name);
```

Here:

```js
(state) => state.user.name;
```

is the **selector**.

It receives the entire Redux state:

```js
{
  user: {
    name: "John",
    email: "john@example.com"
  }
}
```

and returns only:

```js
"John";
```

### Simple definition

> **Selector = a function that reads and returns the data you need from Redux state.**

You can also create reusable selectors:

```js
const selectUserName = (state) => state.user.name;

const name = useSelector(selectUserName);
```

Selectors are useful because they **encapsulate how your component accesses the store** and can help avoid unnecessary re-renders.

22. What are **memoized selectors**?

**Memoized selectors** are selectors that **remember (cache) their previous result** and return the cached result when their inputs haven't changed.

They are useful when a selector performs **expensive calculations**.

### Normal selector

```js
const selectCompletedTodos = (state) =>
  state.todos.filter((todo) => todo.completed);
```

Every time the selector runs, `.filter()` creates a **new array**, even if `state.todos` hasn't changed.

### Memoized selector

Using **Reselect**:

```js
import { createSelector } from "@reduxjs/toolkit";

const selectTodos = (state) => state.todos;

const selectCompletedTodos = createSelector([selectTodos], (todos) =>
  todos.filter((todo) => todo.completed),
);
```

Now the selector remembers the previous result:

```text
todos unchanged
     ↓
return cached array
     ↓
no recalculation
```

If `todos` changes:

```text
todos changed
     ↓
run filter()
     ↓
cache new result
```

### Why use them?

Memoized selectors help with:

- **Avoiding expensive recalculations**
- **Returning the same object/array reference** when inputs haven't changed
- **Reducing unnecessary React-Redux re-renders**

### Interview answer

> **A memoized selector is a selector that caches its result and recalculates only when its input values change. Reselect, commonly used through Redux Toolkit, provides `createSelector` for creating memoized selectors.**

23. How would you prevent unnecessary React re-renders caused by Redux?

To prevent unnecessary React re-renders caused by Redux, I would focus on **selecting only the data the component actually needs** and **keeping selector results referentially stable**.

### 1. Select only required fields

Instead of:

```js
const user = useSelector((state) => state.user);
```

use:

```js
const name = useSelector((state) => state.user.name);
```

If `user.email` changes, a component that only selects `name` doesn't need to re-render because of that change.

---

### 2. Use memoized selectors for derived data

Avoid creating a new array/object on every selector call:

```js
// Can create a new array every time
const completed = useSelector((state) =>
  state.todos.filter((todo) => todo.completed),
);
```

Use a memoized selector instead:

```js
const selectCompletedTodos = createSelector([(state) => state.todos], (todos) =>
  todos.filter((todo) => todo.completed),
);

const completed = useSelector(selectCompletedTodos);
```

The selector can return the **same cached reference** when the input hasn't changed.

---

### 3. Use `React.memo` for child components

If a Redux-connected parent re-renders, a child doesn't necessarily need to.

```js
const UserInfo = React.memo(({ name }) => {
  return <div>{name}</div>;
});
```

`React.memo` can prevent the child from rendering again when its props haven't changed.

---

### 4. Avoid unnecessary object creation in selectors

Be careful with:

```js
const userInfo = useSelector((state) => ({
  name: state.user.name,
  email: state.user.email,
}));
```

This creates a **new object** whenever the selector runs.

Prefer separate selectors:

```js
const name = useSelector((state) => state.user.name);
const email = useSelector((state) => state.user.email);
```

or use an appropriate memoized selector/equality function.

---

### 5. Keep Redux state normalized

For large applications, normalized state can help ensure that updating one entity doesn't require unrelated components to subscribe to a large object.

---

### Interview answer

> **I prevent unnecessary Redux-related re-renders by selecting only the state a component needs, using memoized selectors for derived data, avoiding new object/array references in selectors, and using `React.memo` where appropriate. I also keep the Redux state normalized so updates affect only the relevant parts of the component tree.**

24. How does React-Redux subscription work?

React-Redux uses a **subscription mechanism** to let components know when the Redux store changes.

### How it works

Suppose you have:

```js
const name = useSelector((state) => state.user.name);
```

The flow is roughly:

```text
Component calls useSelector()
        ↓
React-Redux subscribes component to Redux store
        ↓
dispatch(action)
        ↓
Redux updates the store
        ↓
React-Redux is notified
        ↓
Selector runs again
        ↓
Compare previous result with new result
        ↓
Value changed? ── Yes → component re-renders
        │
        └────────────── No → no re-render
```

### Example

Initial state:

```js
{
  user: {
    name: "John",
    email: "john@example.com"
  }
}
```

Component:

```js
const name = useSelector((state) => state.user.name);
```

If an action changes only the email:

```js
dispatch({
  type: "user/emailChanged",
  payload: "new@example.com",
});
```

The selector still returns:

```js
"John";
```

Since the selected value hasn't changed, React-Redux can **skip re-rendering that component**.

If the name changes:

```js
dispatch({
  type: "user/nameChanged",
  payload: "Alice",
});
```

the selector returns a different value:

```text
"John" → "Alice"
```

so the component re-renders.

### Important point

`useSelector()` does **not** simply re-render the component on every Redux update. It subscribes to the store and checks whether **the value returned by that selector has changed**.

By default, React-Redux uses **strict `===` reference equality** for the selected result.

### Interview answer

> **React-Redux subscribes components using `useSelector` to the Redux store. When an action is dispatched and the store updates, React-Redux runs the selector again and compares the new result with the previous result. If the selected value changed, the component re-renders; otherwise, it skips the render.**

25. What is the difference between `useSelector` and `mapStateToProps`?

Both are used to **read Redux state**, but they belong to different React-Redux APIs.

| `useSelector`                             | `mapStateToProps`                      |
| ----------------------------------------- | -------------------------------------- |
| Used with **function components**         | Used with **`connect()`**              |
| React Hook                                | Regular function                       |
| Reads state directly inside the component | Maps Redux state to component props    |
| No need for `connect()`                   | Requires `connect()`                   |
| Modern, recommended approach              | Older/legacy approach, still supported |

### `useSelector`

```js
const name = useSelector((state) => state.user.name);
```

The component directly gets the value from Redux.

```js
function User() {
  const name = useSelector((state) => state.user.name);

  return <h1>{name}</h1>;
}
```

### `mapStateToProps`

```js
const mapStateToProps = (state) => ({
  name: state.user.name,
});

export default connect(mapStateToProps)(User);
```

The selected Redux data becomes a **prop**:

```js
function User({ name }) {
  return <h1>{name}</h1>;
}
```

### Key difference in subscriptions

With `useSelector`, the component subscribes to the store and React-Redux checks the **selector result**.

With `connect`, React-Redux runs `mapStateToProps` and determines whether the resulting props have changed.

### Interview answer

> **`useSelector` is the modern Hook-based way to access Redux state inside function components, while `mapStateToProps` is used with the older `connect()` API to map Redux state into component props. Both allow components to react to relevant Redux state changes, but `useSelector` is generally preferred for modern React code.**

26. What are the advantages/disadvantages of using Redux state directly inside many components?

Using Redux state directly in many components can be useful, but it has trade-offs.

### Advantages

1. **Easy access to shared state**

Any component can access the same data:

```js
const user = useSelector((state) => state.user);
```

No need to pass it through many levels of props.

2. **Less prop drilling**

Instead of:

```text
Parent → Child → Grandchild → UserInfo
```

each component can access Redux directly.

3. **Good for truly global state**

Redux is well suited for things like:

- Authentication/user information
- Shopping cart
- Application settings
- Notifications
- Shared server/cache state

4. **Predictable updates**

State changes happen through Redux actions/reducers, making updates easier to track and debug.

---

### Disadvantages

1. **Components become tightly coupled to Redux**

A component like:

```js
const user = useSelector((state) => state.user);
```

now depends on the structure of the Redux store.

That can make the component harder to reuse or test independently.

2. **Potential unnecessary re-renders**

If components select too much state:

```js
const user = useSelector((state) => state.user);
```

a change anywhere in `user` can cause the component to re-render.

Prefer selecting only what is needed:

```js
const name = useSelector((state) => state.user.name);
```

3. **Redux can become overused**

Not every piece of state needs to be global.

For example, a modal's local open/closed state can usually remain:

```js
const [isOpen, setIsOpen] = useState(false);
```

Putting every small UI state value into Redux adds unnecessary complexity.

4. **Harder to refactor the store**

If many components directly depend on:

```js
state.user.profile.address.city;
```

changing the Redux state structure can require changes across many components.

Using **selectors** helps isolate that dependency.

### Best practice

> **Use Redux for state that genuinely needs to be shared or managed globally, and keep component-specific UI state local. When accessing Redux, prefer focused selectors rather than selecting large portions of the store.**

### Interview answer

> **The main advantage is easy access to shared state and avoiding prop drilling. The disadvantages are tighter coupling to Redux, potential unnecessary re-renders, and overusing global state. I would keep local UI state local and use Redux for genuinely shared application state, preferably accessed through focused selectors.**
